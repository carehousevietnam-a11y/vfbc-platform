[VFBCAI MASTER DEVELOPMENT CONSTITUTION]
PROJECT
VFBCAI — Vietnam Foreign Business Verification & Compliance AI Center
CORE
Check. Verify. Register. Protect.
ROLE
- ChatGPT = Product / UX / Architecture / QA / Final Approval
- Claude / Cursor = Coding / Investigation / Implementation
- Ace = Git push / deployment
- Coding agent는 제품 설계를 임의로 변경하지 않는다.
==================================================
1. ABSOLUTE DEVELOPMENT RULES
==================================================
1) 기존 코드를 먼저 조사한다.
2) 존재하지 않는 파일/함수/DB/API/컬럼을 추측하지 않는다.
3) 한 번에 하나의 기능만 작업한다.
4) 작업 범위를 먼저 고정한다.
5) 지정된 파일 외에는 수정하지 않는다.
6) 기존 구조와 비즈니스 로직을 최대한 보존한다.
7) 불필요한 refactor를 하지 않는다.
8) 새로운 abstraction / 공통화 / 리팩터링은 명시적으로 승인받지 않는 한 금지한다.
9) DB / API / Auth / CRM / Storage / RLS는 작업 범위가 아니면 절대 변경하지 않는다.
10) 이미 정상 작동하는 기능을 작업 편의를 위해 다시 작성하지 않는다.
11) 한 곳의 문제를 해결하기 위해 다른 서비스의 코드를 임의로 변경하지 않는다.
12) 작업 중 발견한 별도 문제는 현재 작업에 섞지 말고 별도 이슈로 분리한다.
==================================================
2. "ONE CHANGE → ONE SCOPE" 원칙
==================================================
하나의 버그를 수정하면서 다른 기능을 함께 개선하지 않는다.
특히 다음을 금지한다.
- UI 개선을 핑계로 로직 변경
- 로직 수정 중 refactor
- 공통화
- 다른 서비스 동시 수정
- DB/API 변경
- 기존 페이지 구조 재설계
- 이름 변경
- 함수 통합
- 사용하지 않는 코드 정리
- lint/style 정리
현재 문제와 직접 관계없는 변경은 하지 않는다.

==================================================
5. RE-ENTRY DESIGN — FIXED POLICY
==================================================
VFBCAI의 모든 CHECK / VERIFY / REGISTER 서비스는
다음 사용자 상태를 명확히 구분한다.
A. NEW CASE
질문
→ Signup
→ Result
→ Documents
B. EXISTING CASE
Landing
→ 기존 Case 복원
→ 기존 Result
→ /mypage
질문을 다시 묻지 않는다.
Signup을 다시 요구하지 않는다.
Documents를 다시 요구하지 않는다.
C. ?start=check
Landing을 건너뛴다.
항상 신규 질문을 시작한다.
기존 Case를 자동 복원하지 않는다.
D. ?restore=1
기존 Case가 있으면 복원한다.
없으면 정상 신규 질문으로 진행한다.
E. LANDING "내 상황 확인하기"
로그인 + 기존 Case
→ 기존 Case 복원
로그인 + 기존 Case 없음
→ 신규 질문
F. RESULT CTA
신규 Case
→ /documents
복원 Case
→ /mypage
이 정책을 임의로 변경하지 않는다.

6. AUTH / SESSION SAFETY
==================================================
세션 관련 코드는 특히 보수적으로 수정한다.
결과 token을 사용하는 경우:
1. lead submit 성공
2. establishBrowserSessionFromResultToken(token)
3. session 성공 확인
4. setResultToken(token)
5. 이후 결과/문서 흐름 진행
세션 생성 실패 시:
- resultToken을 먼저 저장하지 않는다.
- 기존 서비스의 기존 에러 처리 방식을 유지한다.
Prefetch는 기존 browser session을 먼저 확인한다.
session이 이미 존재하면:
- generateLink를 실행하지 않는다.
- 불필요한 magic-link/session race를 만들지 않는다.
이 원칙은 현재 수정 대상 서비스의 실제 기존 구조 안에서
최소 변경으로 적용한다.
TRC의 이미 수정된 session race 해결 코드는
다른 서비스의 수정 근거로만 참고하고,
TRC 자체는 임의 변경하지 않는다.
==================================================
7. REGRESSION PREVENTION
==================================================
모든 수정 전:
A. 현재 동작 확인
B. 관련 함수 확인
C. 관련 파일 확인
D. 변경 범위 확정
수정 후:
A. 변경 diff 확인
B. 변경 파일 확인
C. 기존 로직 보존 여부 확인
D. 다른 서비스에 영향이 없는지 확인
E. tsc 실행
F. 필요한 경우 해당 기능만 QA
"수정했으니 비슷한 곳도 같이 수정"
→ 금지
==================================================
8. DIFF / HUNK DISCIPLINE
==================================================
기존 작업이 working tree에 존재하는 경우
새로운 수정과 기존 수정사항을 반드시 구분한다.
특히 다음을 확인한다.
- 기존 re-entry hunk
- 신규 bug-fix hunk
- 기존 UI 변경
- 신규 session 변경
서로 unrelated한 변경을 하나의 hunk로 섞지 않는다.
작업 종료 보고에는 반드시:
- git diff --name-only
- git diff --stat
- 변경 파일
- 변경 함수
- 신규 변경 목적
- 기존 변경사항 보존 여부
를 보고한다.

10. QA DISCIPLINE
==================================================
QA는 코드 수정과 분리한다.
코드 수정 단계:
- 코드만 수정
- tsc
- diff 확인
QA 단계:
- 실제 UI 검증
- 지정 서비스만 검증
- 지정 횟수만 검증
UI / DESIGN / RESPONSIVE / TYPOGRAPHY FINAL QA:
- PC와 Mobile은 동일 화면의 단순 축소가 아니다.
- PC = Full Information Experience. Mobile = Focused / Simplified Experience.
- business logic과 정보의 의미는 동일하게 유지한다.
- 이 기준 미충족 시 UI QA PASS 금지.
- 전문: `.cursor/rules/06-ui-design-responsive-typography-qa.mdc`
자동 반복 금지.
"1회 실행 → 보고 → 승인 → 다음 1회"
사용자가 승인하지 않은 다음 QA를 자동 실행하지 않는다.
브라우저 자동화:
- 명시적으로 허용된 경우에만 실행
- CDP/localStorage를 통한 세션 강제 조작 금지
- 실제 고객 데이터 사용 금지
- test 계정만 사용
==================================================
11. GIT / DEPLOYMENT SAFETY
==================================================
Coding agent는 명시적 승인 없이:
git add
git commit
git push
하지 않는다.
배포도 임의로 하지 않는다.
특히 working tree에 여러 기능의 변경사항이 존재하면
전체 변경사항을 한 번에 commit하지 않는다.
먼저 diff를 검수하고
어떤 변경을 commit할지 명확히 분리한다.
==================================================
12. WHEN AN UNRELATED BUG IS FOUND
==================================================
현재 작업 중 다른 버그를 발견하면:
1. 현재 작업을 중단하지 않는다.
2. 그 버그를 현재 작업에 섞지 않는다.
3. 원인이 현재 작업에서 새로 발생한 것인지 확인한다.
4. 기존 버그인지 확인한다.
5. 별도 수정 범위로 분리한다.
6. 보고만 한다.
7. 별도 승인 후 수정한다.
이번 tamtru/WP/driving-license session race와 같은 경우에도
이 원칙을 적용한다.

15. RISK-BASED DEVELOPMENT & QA
==================================================
모든 작업에 동일한 검증 강도를 적용하지 않는다.
작업의 위험도에 따라 개발자·검증 절차를 차등 적용한다.

HIGH
예:
- Auth / Session
- 결제
- DB Schema / RLS / Storage
- 핵심 API
- 법령/Legal RAG 핵심 로직
- 기존 사용자 데이터에 영향을 줄 수 있는 변경
절차:
ChatGPT 범위/설계 결정
→ Claude 구현 및 코드 검증
→ tsc + diff 확인
→ Cursor 실브라우저 QA
→ ChatGPT 최종 판단

MEDIUM
예:
- 신규 페이지
- 신규 기능
- 일반 API 변경
- 주요 UX 변경
- 기존 기능에 영향을 줄 수 있는 UI/기능 변경
절차:
ChatGPT 범위 결정
→ Claude 구현
→ tsc + diff 확인
→ 필요할 경우 Cursor 브라우저 QA

LOW
예:
- 문구
- 색상
- 여백
- 아이콘
- 단순 CSS
- 기존 로직에 영향을 주지 않는 시각적 조정
절차:
Ace가 Cursor에 직접 지시 가능
→ Cursor 수정
→ 변경 화면 스크린샷으로 확인
LOW 작업은 Claude 및 ChatGPT의 전체 개발 루프를 반드시 거치지 않는다.

공통 보호 규칙
- 위험도와 무관하게 One Change → One Scope를 유지한다.
- LOW 작업이라도 unrelated refactor는 금지한다.
- LOW 작업에서도 기존 비즈니스 로직과 다른 기능을 변경하지 않는다.
- 변경 파일은 최소화한다.
- AI가 작업 중 발견한 unrelated issue는 현재 작업에 섞지 않는다.
  별도 작업으로 기록하고 현재 작업을 종료한다.
- 동일한 QA 도구의 문제가 반복되면 매번 임기응변으로 우회하지 않고
  QA 인프라 개선 작업으로 분리한다.
- QA 도구의 한계와 제품 버그를 혼동하지 않는다.
- 검증 수준은 위험도에 비례하여 결정한다.

역할 분리
- ChatGPT: Product / UX / Architecture / Risk 판단 / 최종 QA
- Claude: 코드 조사 및 구현
- Cursor: 작업 실행, 브라우저 QA, Git, 배포
- Ace: 최종 승인 및 배포 판단
단, LOW 작업에서는 Ace → Cursor 직접 작업을 허용한다.

16. CASE CONTINUITY / EXPERT HANDOFF — MASTER 원칙
==================================================
본 절은 §5 Re-entry(세션·Case 복원) 및 `vfbcai-funnel-profile.mdc`(질문·Profile·1차/2차)와
함께 적용한다. 충돌 시 본 절의 Master 데이터 축적·전문가 연결 원칙이 우선한다.
Re-entry는 "같은 Case를 다시 시작하지 않음"을, 본 절은 "한 Case 안에서
정보를 계속 축적하고 반복 설명 없이 전문가에게 연결"을 규정한다.

16.1 최종 목적 — 반복 설명 없는 전문가 연결
VFBCAI의 질문·프로파일링·증거 수집의 최종 목적은
단순히 AI가 질문을 많이 하는 것이 아니다.
고객이 CHECK / VERIFY / REGISTER / PROTECT 과정을 거치는 동안
확보된 모든 유의미한 정보를 하나의 구조화된 Case Profile로 축적하여,
고객이 최종적으로 전문가 진행을 선택했을 때
전문가가 고객에게 처음부터 동일한 사건을 다시 설명하도록 요구하지 않고
이미 축적된 데이터를 기반으로 바로 사건 해결에 집중할 수 있도록 하는 것이
VFBCAI의 핵심 시스템 목적이다.

16.2 SINGLE SOURCE OF CASE TRUTH
한 번 확보된 고객 정보는 이후 단계의 기본 데이터로 사용한다.
다음 정보는 Case Profile의 지속적인 데이터 자산으로 취급한다.
- 최초 고객 자연어 입력
- 1차 질문 답변
- 2차 개인화 질문 답변
- 고객 직접 입력
- 선택한 상황/사건 정보
- 문서에서 확인된 사실
- 영수증/계약서/공문 등 제출 증거
- 문서에서 추출된 날짜·금액·당사자·조건 등 구조화 정보
- 사건 경과
- 상대방 정보
- 고객의 목표
- 확인된 사실
- 고객의 주장/추정
- 미확인 사실
- 상충 정보
- 누락 정보
- 핵심 쟁점
- 위험 요인
- 해결 경로 / CASE
- 전문가에게 전달해야 할 핵심 정보
이후 질문과 결과는 가능한 한 이 Profile을 기반으로 생성한다.

16.3 NEVER ASK AGAIN
이미 충분히 확보된 정보를 동일하거나 거의 동일한 의미로 다시 질문하지 않는다.
특히 다음을 금지한다.
- 1차에서 확인한 사실을 2차에서 다시 묻는 것
- 문서에서 확인 가능한 사실을 고객에게 다시 묻는 것
- 이전 답변으로 이미 판단 가능한 내용을 다시 묻는 것
- 고객이 직접 입력한 내용을 다시 확인하는 단순 반복 질문
- 전문가 연결 직전에 사건 전체를 처음부터 다시 설명하게 만드는 질문
단, 기존 정보가 서로 충돌하거나,
해결 판단에 중요한 추가 사실이 필요하거나,
기존 정보의 정확한 범위를 확인해야 하는 경우에는
그 이유가 명확한 후속 질문을 허용한다.
(§5 EXISTING CASE의 "질문을 다시 묻지 않는다"와 동일 방향 — 세션 복원 + Case 내 연속성.)

16.4 질문은 '반복'이 아니라 '깊이'를 만든다
1차 질문은 사건/상황의 기본 구조를 확보한다.
2차 질문은 1차에서 이미 확보된 정보를 기반으로
개인의 실제 사건을 더 깊게 추적한다.
2차 질문은 1차 질문의 단순 반복이나 동일한 질문의 세분화가 아니다.
예:
1차: "계약 후 문제가 발생했습니다."
2차: "계약 후 문제가 발생했다고 답변하셨습니다.
현재까지 실제로 이행되지 않은 내용은 무엇이며,
상대방에게 이를 요청하거나 이의를 제기한 경우
언제, 어떤 방식으로 전달했는지 알려주세요."
즉, 기존 정보 → 새로운 핵심 사실 → 다음 질문 의 연결 구조를 유지한다.

16.5 DOCUMENT-FIRST 원칙
문서가 제공하는 정보는 질문보다 우선하여 활용한다.
예: 영수증에서 거래일·금액·거래 상대방이 확인되면,
이를 다시 단순 질문하지 않고 Profile에 반영한 뒤
그 사실과 관련된 다음 판단에 필요한 질문을 생성한다.
문서가 여러 질문을 대체할 수 있다면
불필요한 질문을 줄이고 문서 증거를 활용한다.

16.6 1차와 2차의 정보 밀도
1차는 고객이 현재 상황을 이해하고 기본적인 사건 구조를 형성할 수 있도록 한다.
2차는 개인화된 사건 판단을 위해 더 높은 정보 밀도를 가져야 한다.
질문 수를 고정하지 않는다.
(예: 총 14개 필요 시 1차 약 5 + 2차 약 9 — 숫자는 예시, 기준은 고정 개수가 아님.)
중요한 기준: 1차 < 2차 의 정보 깊이와 개인화 수준.
2차 질문은 1차 답변과 제출 증거를 기반으로
실제 사건 해결에 필요한 정보를 추가 확보해야 한다.

16.7 질문 품질 GATE
모든 질문은 구현·설계 전에 다음을 통과해야 한다.
① 이미 확보된 정보를 다시 묻고 있지 않은가?
② 이 질문의 답변이 어떤 결과 판단에 사용되는가?
③ 이전 답변/문서와 논리적으로 연결되는가?
④ 실제 고객의 상황을 구분할 수 있는 질문인가?
⑤ 선택지가 실제 상황을 충분히 표현하는가?
⑥ 짧은 단어/추상적 선택지만으로 중요한 사건을 축약하고 있지 않은가?
⑦ 선택지가 맞지 않을 경우 직접 입력할 수 있는가?
⑧ 답변이 Case Profile에 구조화되어 저장되는가?
⑨ 이후 질문이나 결과에서 이 정보가 실제로 활용되는가?
⑩ 전문가 연결 시 실제 사건 해결에 도움이 되는 정보인가?
하나라도 충족하지 못하면 질문을 구현하지 않는다.

16.8 ANSWER → PROFILE → RESULT → EXPERT HANDOFF
모든 수집 정보는 다음 구조를 따른다.
고객 입력 → 질문 답변 → 문서/증거
→ Situation Profile → Case Profile
→ 핵심 쟁점 / 사실 / 미확인 정보 / 위험 / 해결목표
→ 개인화 결과 → 전문가 전달용 사건 정보
결과 화면의 중요한 판단은 가능한 한 Profile의 실제 데이터에 근거해야 한다.
전문가 연결 시 Case Profile을 기반으로
사건을 바로 검토할 수 있는 상태를 목표로 한다.

16.9 EXPERT HANDOFF 성공 기준
전문가 진행 단계에서 다음을 고객에게 처음부터 반복하지 않는 것이
데이터 축적의 핵심 성공 기준이다.
금지되는 실패 사례(이미 VFBCAI에서 확보된 정보라면):
"처음부터 무슨 일이 있었는지 설명해주세요."
"계약은 언제 했나요?" / "얼마를 지불했나요?"
"어떤 서류를 가지고 있나요?" / "상대방은 누구인가요?" / "무엇이 문제인가요?"
전문가에게 필요한 추가 질문은 허용하되,
'처음부터 다시 수집'이 아니라 '이미 축적된 Profile 기반 해결 단계 질문'이어야 한다.

16.10 DATA ASSET 원칙
고객의 답변과 증거는 단순 UI 상태값으로 취급하지 않는다.
구조화된 데이터는 장기적으로 Case 축적·유사 사건 분류·전문가 업무 지원·
사건 패턴 분석·서비스 개선·콘텐츠(SEO/AEO/GEO/LLMO) 등에 활용 가능하도록 설계한다.
개인정보·민감정보는 목적과 권한에 맞게 처리하며
불필요한 개인정보를 데이터 자산으로 축적하지 않는다.

16.11 MASTER 적용 범위
Real Estate VERIFY는 이 구조를 검증하는 MASTER 서비스다.
이후 동일 Master Architecture를
VERIFY(행정문서·사기·세금·기타), CHECK, REGISTER, PROTECT에 확장한다.
서비스별 변경 가능: domain questions, Situation Profile fields, CASE,
evidence types, result content, expert handoff fields.
변경 불가 Master 원칙:
"기존 데이터를 기반으로 다음 정보를 추적하고
최종적으로 반복 설명 없는 전문가 연결을 만든다."

16.12 IMPLEMENTATION RULE
새 질문/프로파일링/결과/전문가 연결 기능 구현 시
본 Skill(`.cursor/skills/vfbcai-master-development/SKILL.md`)과 §16을 먼저 참조한다.
이미 검증·확정된 질문·선택지·Situation Profile·CASE·결과 구조가 있으면
새 구조를 임의 발명하지 말고 기존 구조를 재사용·확장한다.
Admin VERIFY의 기존 상세 2차 개인화 질문 구조처럼
검증된 상세 질문 구조가 있으면 Real Estate Master 및 후속 서비스의
우선적 구조적 참고 모델로 사용한다.

16.13 최종 MASTER 문장
VFBCAI는 고객에게 같은 이야기를 반복하게 만드는 시스템이 아니라,
고객이 한 번 제공한 정보와 증거를 계속 축적하여
다음 단계의 질문과 판단에 활용하고,
최종적으로 고객과 전문가가 이미 정리된 사건을 기반으로
바로 해결에 집중할 수 있도록 하는 시스템이다.
VFBCAI의 질문은 '정보 수집'에서 끝나는 것이 아니라
'사건의 연속성을 유지하는 데이터 축적'을 목적으로 한다.
