# VFBCAI MASTER DEVELOPMENT SKILL

## Universal Situation-Driven Development & Question Architecture

### Consolidated Master v1.2 --- 2026-09-18

------------------------------------------------------------------------

# 0. 문서의 지위

본 문서는 현재까지 확정된 VFBCAI 개발 원칙, 행정문서 MASTER에서 검증된
개발 방법, 질문·선택지 정제 프로토콜, 그리고 향후 CHECK / VERIFY /
REGISTER / PROTECT 전체에 적용할 Universal Situation-Driven Question
Architecture를 하나로 통합한 MASTER 기준이다.

최신 확정 기준이 과거 기준보다 우선한다.

문서 간 충돌이 발생하면 최신 확정 기준과 본 MASTER의 최신 조항을
우선한다.

------------------------------------------------------------------------

# 1. VFBCAI 제품 개발의 최우선 철학

VFBCAI는 질문을 많이 하는 서비스가 아니다.

> 사용자가 자신의 상황을 설명하면, VFBCAI가 전문가처럼 핵심 사실을
> 추적하고 다음 판단으로 연결하는 서비스다.

따라서 질문 경험은:

상황 파악 → 핵심 쟁점 발견 → 필요한 사실 추적 → 판단 → 다음 행동

으로 느껴져야 한다.

단순히:

질문 → 질문 → 질문

의 설문 경험이 되어서는 안 된다.

------------------------------------------------------------------------

# 2. VFBCAI 전체 서비스 구조

VFBCAI의 기본 구조는 변경하지 않는다.

-   CHECK --- 확인
-   VERIFY --- 검토
-   REGISTER --- 인허가
-   PROTECT --- 진단

각 전문 영역은 서로의 역할을 혼용하지 않는다.

VFBCAI의 질문·상황추적 아키텍처는 VERIFY에만 한정하지 않는다.

다음 전체 영역에 공통 적용한다.

-   법률
-   행정
-   인허가
-   진단
-   문서
-   부동산
-   세금
-   사기
-   향후 추가되는 모든 전문 서비스

------------------------------------------------------------------------

# 3. Universal Situation-Driven Question Architecture

VFBCAI의 핵심 질문 시스템은 고정된 질문 목록을 사용자에게 순차적으로
제시하는 단순 설문 시스템이 아니다.

사용자는 첫 화면에서 자신의 상황을 자연어로 직접 설명할 수 있어야 한다.

기본 흐름:

Customer Initial Question ↓ Situation Understanding ↓ Situation Profile
↓ Domain / Service Identification ↓ Key Issue Identification ↓ Missing
Fact Identification ↓ Adaptive Questions ↓ Context-specific Answer
Choices ↓ Situation Profile Refinement ↓ CHECK / VERIFY / REGISTER /
PROTECT 판단 ↓ Personalized Result ↓ Next Action

사용자의 최초 질문은 단순 검색어가 아니라 Situation Input으로 취급한다.

------------------------------------------------------------------------

# 4. 최초 자유질문의 역할

예:

"베트남에서 식당을 열려고 하는데 외국인 명의로 가능한지, 어떤 허가가
필요한지 모르겠습니다."

"집주인이 보증금을 돌려주지 않고 있는데 계약서에는 반환한다고 되어
있습니다."

"사업자 등록은 했는데 지금 어떤 허가를 추가로 받아야 하는지
모르겠습니다."

이러한 입력은 모두 유효한 Initial Situation Input이다.

가능한 범위에서 다음 정보를 구조화한다.

-   Who
-   What
-   Where
-   When
-   Stage
-   Problem
-   Claim
-   Counterparty
-   Authority
-   Document
-   Amount
-   Deadline
-   Goal

단, 입력에서 확인되지 않은 사실을 추측하여 확정하지 않는다.

------------------------------------------------------------------------

# 5. Situation Profile

Situation Profile은 모든 서비스를 하나의 거대한 고정 스키마로 묶는
방식이 아니다.

## 5.1 공통 Core Profile

기본적으로 다음 축을 고려한다.

-   Domain
-   Service
-   Situation
-   Stage
-   User Position
-   Counterparty / Authority
-   Actual Facts
-   Claims
-   Evidence
-   Documents
-   Dates
-   Deadline
-   Amount
-   Actions Taken
-   Responses
-   Current Blockage
-   Customer Goal

## 5.2 Domain-specific Profile

공통 Profile 위에 전문 영역별 필드를 추가한다.

예:

부동산: - Property - Ownership - Contract - Transaction

행정: - Authority - Application - Submission - Administrative Stage

인허가: - Business Type - Permit Type - Facility - Authority -
Requirements

법률: - Claim - Dispute - Rights - Evidence - Counterparty

진단: - Current State - History - Risk - Evidence

모든 필드를 반드시 질문하지 않는다.

결과 판단에 필요한 정보만 질문으로 변환한다.

------------------------------------------------------------------------

# 6. CASE의 정의

CASE는 질문의 전체 목록이 아니다.

CASE의 목적은:

> 현재 사용자의 상황에서 VFBCAI가 따라가야 할 판단·검토·처리 경로를
> 결정하는 것

이다.

따라서 CASE의 개수를 사전에 6개, 7개, 10개 등으로 고정하지 않는다.

실제 전문가의 판단 구조를 분석한 결과로 CASE를 정의한다.

새로운 상황이 발견되면 기존 CASE에 무조건 강제하지 않는다.

Situation Profile ↓ 현재 핵심 쟁점 ↓ 기존 Resolution Path 적합성 확인 ↓
필요 시 새로운 Resolution Path 정의

로 판단한다.

------------------------------------------------------------------------

# 7. CASE와 질문의 관계

CASE가 질문 목록을 직접 결정하는 구조로 만들지 않는다.

올바른 구조:

Initial Input ↓ Situation Profile ↓ 현재 확인된 사실 ↓ 아직 확인되지
않은 핵심 사실 ↓ 전문가 판단에 필요한 정보 ↓ Question Selection ↓
Adaptive Branch

따라서 동일한 CASE라도 사용자의 최초 질문과 이미 제공한 정보에 따라 서로
다른 질문과 선택지가 나타날 수 있다.

------------------------------------------------------------------------

# 8. 질문 설계의 핵심 원칙

모든 질문은 다음 질문에 답할 수 있어야 한다.

> 이 답변이 결과에서 무엇을 판단하는 데 사용되는가?

답할 수 없으면 해당 질문을 만들지 않는다.

질문 하나하나는:

사용자 답변 → 상황 데이터 구조화 → 전문가가 추적하는 핵심 사실 → 판단 →
위험/확인사항 → 다음 행동

으로 연결되어야 한다.

------------------------------------------------------------------------

# 9. 질문·선택지 정제 프로토콜

질문은 바로 UI에 넣지 않는다.

다음 순서를 반드시 거친다.

전문가의 실제 판단 구조 ↓ 필요한 사실 추출 ↓ 질문 후보 작성 ↓ 질문 목적
검증 ↓ 선택지별 실제 상황 구분 ↓ 추상적/중복 선택지 제거 ↓ Situation
Profile 연결 ↓ 1차 결과 연결 ↓ 2차 Adaptive Branch 연결 ↓ 결과 변화 여부
검증 ↓ 최종 질문/선택지 확정 ↓ UI 구현

------------------------------------------------------------------------

# 10. 질문 최종 검증 10개 항목

모든 질문은 UI 구현 전에 다음을 통과해야 한다.

1.  실제 상황을 구분하는가?
2.  선택지가 실제 상황의 차이를 표현하는가?
3.  사용자가 자신의 상황을 선택할 수 있는가?
4.  전문가가 답변의 의미를 해석할 수 있는가?
5.  Situation Profile에 구조화되는가?
6.  1차 결과에 영향을 주는가?
7.  또는 2차 Adaptive Branch에 영향을 주는가?
8.  또는 최종 결과/다음 행동에 영향을 주는가?
9.  이미 확보한 정보를 다시 묻지 않는가?
10. 새로운 상황을 불필요하게 "기타"로 보내지 않는가?

하나라도 충족하지 못하면 UI 구현 전에 질문을 다시 정제한다.

------------------------------------------------------------------------

# 11. 질문의 길이와 Sharp 원칙

짧은 질문이 좋은 질문이라는 뜻이 아니다.

> Sharp = 짧음이 아니다.

Sharp는:

> 실제 업무에서 중요한 차이를 정확하게 구분하는 것

이다.

질문과 선택지는 사용자가 읽었을 때:

> "내 상황은 이것에 가깝다."

라고 판단할 수 있어야 한다.

전문가가 읽었을 때:

> "이 선택을 했다는 것은 이런 사실을 의미한다."

라고 해석할 수 있어야 한다.

단, 불필요하게 긴 설명을 넣어서는 안 된다.

------------------------------------------------------------------------

# 12. 추상적 선택지 금지

다음과 같은 선택지는 최종 질문에서 사용하지 않는다.

-   이유
-   금액
-   서류
-   기타
-   잘 모르겠음
-   문제가 있음
-   제출함
-   확인 필요

이러한 표현은 실제 상황을 충분히 구분하지 못하고 전문가가 상황을
복원하기 어렵다.

------------------------------------------------------------------------

# 13. 상황이 보이는 선택지

선택지는 실제 상황이 드러나는 문장으로 작성한다.

나쁜 예:

현재 상황은? - 문제가 있음 - 처리 중 - 완료 - 기타

정제 방향:

현재 해당 업무는 어느 단계까지 진행된 상태인가요?

-   아직 관련 기관에 신청하거나 서류를 제출하지 않은 상태입니다.
-   서류를 준비하거나 작성하고 있지만 아직 기관에 제출하지 않았습니다.
-   이미 서류를 제출했으며 현재 기관의 검토나 처리를 기다리고 있습니다.
-   기관에서 보완이나 추가 자료 제출을 요청받아 대응하고 있습니다.
-   처리가 완료되었지만 결과나 발급된 서류의 내용을 다시 확인하고
    싶습니다.
-   위 상황 중 정확히 맞는 항목이 없어 현재 상황을 직접 설명하고
    싶습니다.

핵심은 문장을 길게 만드는 것이 아니라 각 선택지가 서로 다른 실제 상황을
의미하도록 만드는 것이다.

------------------------------------------------------------------------

# 14. 질문의 실제 업무 기준

각 신규 서비스마다 먼저 전문가가 실제로 추적하는 핵심 사실을 정리한다.

최소한 다음 범주를 검토한다.

-   사건/문서의 종류
-   발생한 실제 상황
-   사용자의 주장
-   기관/상대방의 주장
-   사실관계의 차이
-   현재 처리 단계
-   이미 취한 조치
-   기관/상대방의 반응
-   날짜/기한
-   금액
-   장소
-   관련 서류/증거
-   현재 장애요인
-   사용자가 원하는 해결 방향

모든 항목을 무조건 질문하지 않는다.

결과 판단에 필요한 경우만 질문한다.

------------------------------------------------------------------------

# 15. 질문은 "다음에 필요한 정보"를 기준으로 한다

현재까지 알고 있는 정보만으로 판단할 수 없다면 무엇을 더 알아야 하는지
찾는다.

예:

사용자: "계약은 했는데 보증금을 못 받았습니다."

이미 알고 있는 정보: - 계약 체결 - 보증금 - 반환 문제

따라서 다시 "계약하셨나요?"를 묻지 않는다.

대신 필요한 정보 중 상황에 맞는 것을 선택한다.

-   계약 종료 여부
-   반환 약정
-   반환 예정일
-   상대방의 주장
-   이미 요청했는지
-   상대방의 반응
-   증거

질문은 고정된 순서가 아니라 현재 Profile의 부족한 핵심 정보를 채우는
방식으로 작동한다.

------------------------------------------------------------------------

# 16. 질문 수를 인위적으로 맞추지 않는다

특정 MASTER 서비스가 4문항이라고 해서 다른 서비스도 무조건 4문항으로
만들지 않는다.

2차 질문도 같은 개수를 맞추기 위해 불필요한 질문을 만들지 않는다.

기준은:

> 최소 질문으로 최대한의 실제 판단 정보를 확보한다.

------------------------------------------------------------------------

# 17. Adaptive Question 원칙

질문 수를 고정하지 않는다.

필요한 질문만 추가한다.

특정 상황이 명확하게 분류되었다면 그 상황과 관계없는 질문은 제거한다.

특정 위험이나 불확실성이 발견되면 해당 부분을 추가 확인한다.

핵심:

> 1차에서 이미 알고 있는 사실을 2차에서 다시 질문하지 않는다.

2차 질문은 1차 답변을 전제로 더 깊게 들어간다.

------------------------------------------------------------------------

# 18. 직접 설명하기

사용자가 기존 선택지에 자신의 상황을 정확히 맞추기 어려운 경우를 반드시
고려한다.

직접 설명 입력은 단순 `other`로 버리지 않는다.

직접 설명:

1.  해당 내용을 상황 데이터로 보존
2.  가능한 경우 상황 분류에 활용
3.  분류가 불가능하면 불명확/fallback 성격으로 처리
4.  사용자의 직접 설명을 결과에서 무시하지 않는다.

처리 구조:

Natural Language ↓ Situation Extraction ↓ Profile Update ↓
Reclassification ↓ Additional Question

CASE_07 같은 임의 CASE를 만들어 문제를 해결하지 않는다.

------------------------------------------------------------------------

# 19. 새로운 질문에도 대응할 수 있는 구조

VFBCAI는 미리 예상한 질문만 처리하는 시스템이 되어서는 안 된다.

새로운 질문이 들어오면:

Customer Question ↓ Situation Profile ↓ Domain / Situation / Stage / Key
Issue ↓ 필요 정보 식별 ↓ 해당 정보에 맞는 Question Library 선택 ↓ 상황에
맞는 선택지 구성 ↓ Adaptive Branch ↓ 개인화 결과

로 처리할 수 있어야 한다.

예:

"외국인인데 베트남 아파트를 공동명의로 구입할 수 있는지 확인하고
싶습니다."

이 경우 기존에 "외국인 공동명의"라는 고정 질문이 없어도 Profile을 통해:

-   Transaction = Purchase
-   User = Foreigner
-   Ownership = Joint
-   Stage = Pre-contract
-   Goal = Eligibility / Ownership verification

등을 구조화하고 필요한 질문을 선택할 수 있어야 한다.

------------------------------------------------------------------------

# 20. Question Library

질문은 단순 페이지별 문구가 아니라 재사용 가능한 지식 자산으로 취급한다.

Question Library는 다음과 같은 목적을 가진다.

-   상황별 질문 후보 저장
-   질문 목적 정의
-   Profile field 연결
-   선택지 의미 정의
-   Branch 조건 정의
-   결과 연결 정의
-   중복 질문 방지
-   향후 새로운 상황에 대한 재사용

단, 동일 문장을 모든 서비스에 기계적으로 복사하지 않는다.

질문의 구조적 원칙은 공유하되 실제 질문과 선택지는 전문 영역의 판단
구조에 맞게 설계한다.

------------------------------------------------------------------------

# 21. Answer → Situation Profile → Judgment

질문과 결과의 연결은 반드시 확인한다.

예:

Q1 answer → Situation Profile → Result 01

Q2 answer → Confirmation Goal → Result 02/04

Q3 answer → Response History → Risk

Q4 answer → Deadline → Next Action

2차도 동일하다.

답변했는데 결과가 변하지 않는 질문은 제거하거나 연결을 수정한다.

------------------------------------------------------------------------

# 22. 1차 결과 구조

1차 결과는 단순히:

"확인 필요합니다."

라고 끝나면 안 된다.

기본 구조:

## 01 전체 판단

현재 답변으로 파악되는 상황을 자연어로 설명한다.

## 02 핵심 확인 결과

사용자의 주요 답변에서 도출된 핵심 판단.

## 03 주요 위험 요인

현재 단계에서 놓치기 쉬운 위험.

## 04 확인이 필요한 사항

아직 확정할 수 없는 부분.

## 다음 단계

왜 2차 검토가 필요한지 자연스럽게 연결한다.

질문과 답변을 raw text로 그대로 보여주지 않는다.

결과는:

Answer → Situation Profile → Judgment

구조로 변환한다.

# 23. 2차 개인화 결과

2차 결과는 1차보다 구체적이어야 한다.

1차: 현재 상황에서 무엇을 확인해야 하는지

2차: 사용자가 실제로 어떤 상황에 놓여 있고 무엇이 핵심 쟁점인지

기본 구조:

01 개인화된 상황 판단 02 핵심 확인 결과 03 주요 위험/불확실성 04 추가
확인이 필요한 사항 05 다음 단계 액션

기본 CTA:

-   AI 리포트 준비하기
-   전문가 검토 요청하기

직접 처리하기 CTA, 직접 대응하기 CTA, 별도 법률 안내문, QUESTION GUIDE,
OFFICIAL SOURCES, 1차와 동일한 CTA 구조를 2차 결과에 임의로 추가하지
않는다.

# 24. 1차 / 2차 UI 차별화

1차와 2차가 완전히 동일한 화면처럼 보이면 안 된다.

전체 브랜드 구조는 유지한다.

1차: 사용자의 기본 상황을 빠르게 파악하는 단계.

2차: 개인화된 깊은 검토 단계.

따라서 색감, 정보밀도, step 표시, 결과 표현 등에서 단계가 깊어졌다는
느낌을 줄 수 있다.

행정문서에서 확정된 Stitch UI를 기준으로 하며 임의로 새로운 디자인
시스템을 만들지 않는다.

# 31. 과거 Stitch 문제 재발 방지

## 문제 1 --- Global CSS가 결과 카드 grid까지 변경

질문용 global selector가 결과 화면의 grid를 1열로 변경한 사례가 있었다.

예방: selector 변경 시 질문 화면 이외의 결과 화면에 영향을 주는지 반드시
확인한다.

특히: - `!important` - broad selector - `.grid` - `.gap-*` - responsive
override - parent selector

를 확인한다.

## 문제 2 --- Parent wrapper 차이

Stitch 부모 wrapper와 실제 구현 wrapper가 달라 전체 폭과 padding이
어긋날 수 있다.

예방: parent wrapper까지 원본 DOM 기준으로 재현한다.

## 문제 3 --- Raw Q&A 결과

질문과 답변을 결과에 그대로 노출하지 않는다.

## 문제 4 --- 1차/2차 중복

1차에서 확보한 사실을 Profile에 보존하고 2차에서 제외한다.

## 문제 5 --- Adaptive branch와 QA harness 충돌

제품 문제인지 QA harness 문제인지 먼저 구분한다.

## 문제 6 --- 짧은 선택지

짧은 선택지 때문에 사용자가 자신의 상황을 정확히 선택하지 못하는 문제를
방지한다.

# 32. QUESTION GUIDE

1차:

"질문 하나하나가 다음 판단으로 연결됩니다."

2차:

"이제 내 상황을 조금 더 깊게 확인합니다."

1차 답변을 바탕으로 놓치기 쉬운 부분을 추가로 확인합니다. 자세히
답해주실수록 더 정확한 개인화 결과를 받을 수 있습니다.

구조:

QUOTATION REPORT ↓ QUESTION GUIDE ↓ OFFICIAL SOURCES

QUESTION GUIDE를 독립 sticky/fixed로 만들지 않는다.

# 38. CASE 체계 보호

CASE 수를 인위적으로 제한하지 않는다.

CASE는 실제 전문가 판단 구조를 반영해야 한다.

불명확한 상황은 적절한 fallback/reclassification 경로로 처리한다.

임의의 CASE_07을 단순히 "기타" 해결책으로 생성하지 않는다.

기존 서비스의 확정 CASE 체계는 해당 서비스의 MASTER 기준을 따른다.

방안을 먼저 검토한다.

부동산에서는 최소한 다음 판단 축을 검토한다.

-   거래
-   계약
-   임대차
-   권리
-   등기
-   금전
-   분쟁
-   중개
-   개발/건축
-   기타 상황

그러나 이 목록을 최종 CASE 수로 고정하지 않는다.

-   Money
-   Dates

-   Responses
-   Rights
-   Evidence
-   Risk
-   Goal

등을 필요에 따라 활용한다.

# 44. 부동산에서 새로운 질문을 처리하는 예

사용자:

"베트남에서 상가를 임대하려고 하는데 건물주가 아닌 사람이 계약하자고
합니다. 이 사람이 실제로 계약할 권한이 있는지 확인하고 싶습니다."

가능한 Profile:

-   Transaction = Lease
-   Stage = Pre-contract
-   Property = Commercial
-   Key Issue = Authority
-   Counterparty = Non-owner
-   Goal = Verify contracting authority

그 다음 필요한 질문을 선택한다.

예:

"현재 계약하려는 상대방과 건물의 소유자 관계를 알고 있나요?"

선택지는 실제 상황을 구분하도록 작성한다.

-   건물 소유자가 직접 계약하려고 합니다.
-   소유자의 직원이나 관리자가 대신 계약하려고 합니다.
-   소유자가 아닌 별도의 회사나 개인이 계약하려고 합니다.
-   상대방이 어떤 권한으로 계약하는지 아직 확인하지 못했습니다.
-   계약 상대방과 소유자의 관계를 확인할 수 있는 자료가 있습니다.

답변에 따라:

비소유자 ↓ 대리권 확인 ↓ 위임장 존재? ↓ 위임 범위? ↓ 소유자 확인 가능? ↓
증거 확인

처럼 adaptive branch를 구성할 수 있다.

# 45. 결과는 상황을 판단해야 한다

"현재 상황은 무엇인가요? 기타."

행동

으로 변환한다.

예:

"현재까지 관련 자료를 제출하지 않은 상태로 보여, 기관이 요구하는 자료의
범위와 제출 방식부터 확인할 필요가 있습니다."

# 51. MASTER QUESTION ARCHITECTURE — FINAL / PERMANENT

## 51.1 이 조항의 지위

본 조항은 기존 VFBCAI MASTER에 이미 확정되어 있던
Situation-Driven Question Architecture, Situation Profile, CASE,
Adaptive Branch, Question Library, 질문·선택지 정제, 1차/2차 개인화,
Case Continuity, Evidence 축적, Expert Handoff 원칙을 폐기하지 않는다.

오히려 이 원칙들을 하나의 최종 질문 아키텍처로 통합하고 명확하게 한다.

특히 과거 개발 과정에서 **ONE RESULT를 만들기 위한 일시적인 단순화**로
질문의 깊이와 추적 범위가 축소되어서는 안 된다.

이 조항과 기존 조항이 충돌하는 경우, 본 조항을 최신 확정 기준으로
적용한다.

## 51.2 최종 목적

VFBCAI의 질문 퍼널은 단순한 설문조사나 결과 생성기가 아니다.

최종 목적은:

> 고객이 자신의 상황을 설명하면 VFBCAI가 사건을 하나의 Case로
> 추적·구조화하고, 필요한 사실·관계·행위·시간·문서·증거·주장·반응을
> 단계적으로 확인하여, 전문가가 고객에게 같은 사건을 처음부터 다시
> 묻지 않아도 될 정도의 Case Profile을 축적하는 것이다.

따라서 질문의 성공 기준은 **질문 수가 적은 것**이나 **결과가 빨리 나오는 것**이
아니다.

성공 기준은:

> **필요한 사실을 놓치지 않으면서 불필요한 반복을 하지 않고,
> 사건을 최대한 정확하게 재구성하는 것**이다.

## 51.3 Investigative / Profiling 방식의 적용

VFBCAI는 범죄 수사나 범죄자 프로파일링의 UI를 복제하는 것이 아니다.

그러나 복잡한 사건을 추적하는 **조사·프로파일링 사고방식**을 질문
아키텍처에 적용한다.

즉 하나의 목표나 주장만 보고 결론을 내리지 않고:

목표 / 주장
↓
사건의 시작점
↓
시간순서
↓
관련 인물·기관·당사자
↓
각자의 행동
↓
상대방의 행동과 반응
↓
계약·문서·조건
↓
금액·재산·의무
↓
실제 발생 사실
↓
진술 / 주장
↓
증거 / 자료
↓
증거와 진술의 일치·불일치
↓
연관 관계
↓
가능한 원인·경과·결과
↓
현재 상태
↓
핵심 쟁점
↓
해결 목표

를 서로 연결하여 하나의 Situation / Case Graph에 가깝게 축적한다.

단, **확인되지 않은 추측을 사실로 저장하지 않는다.**

Profile은 최소한:

- Confirmed Fact
- Customer Claim
- Counterparty Claim
- Inferred / Possible Relationship
- Unknown / Unverified Fact
- Evidence

를 구분할 수 있어야 한다.

## 51.4 최고 전문가 수준의 질문 기준

VFBCAI의 질문은 사용자의 편의를 위해 지나치게 단순화된 질문만을
사용하지 않는다.

전문가가 실제 사건을 해결하기 위해 필요한 정보라면 질문이 길어지거나
세부 Branch가 많아지는 것을 정상적인 결과로 인정한다.

중요한 것은 질문의 숫자가 아니라 **정보의 깊이와 연결성**이다.

따라서 복잡한 사건에서 다음과 같은 흐름은 정상이다.

질문
→ 답변
→ Profile 갱신
→ 새로운 단서 발견
→ 관련 사실 질문
→ 답변
→ 다른 Branch 발생
→ 시간/금액/문서/행위 확인
→ 증거 확인
→ 모순 확인
→ 추가 질문
→ Profile 정교화
→ 사건 재구성
→ 충분성 판단
→ 다음 단계

이 과정에서 질문이 10개, 15개, 20개 이상이 되더라도
그 질문들이 실제 사건 추적에 필요하다면 불필요한 질문으로 간주하지 않는다.

반대로 단순한 사건이 충분히 확인된 경우에는 짧게 종료할 수 있다.

**복잡도가 질문량을 결정한다.**

## 51.5 질문량의 원칙 — 적게가 아니라 정확하게

기존 MASTER의

> 최소 질문으로 최대한의 실제 판단 정보를 확보한다.

라는 표현은 **질문을 적게 하라는 의미가 아니다.**

최종 의미는 다음과 같다.

> **불필요한 질문은 하지 않되, 필요한 질문은 사건이 충분히 재구성될
> 때까지 생략하지 않는다.**

따라서 다음 두 극단을 모두 금지한다.

### 금지 A — 과잉 질문

이미 확인된 사실을 반복하거나 결과와 전문가 판단에 아무런 영향을 주지
않는 질문을 계속하는 것.

### 금지 B — 조기 종료

대략적인 결과를 만들 수 있다는 이유만으로 중요한 사실이 비어 있는데
질문을 종료하는 것.

## 51.6 1차 / 2차의 관계

1차와 2차는 단순한 무료/유료 질문 개수 차이가 아니다.

### 1차

고객의 최초 상황을 이해하고 사건의 기본 골격을 만든다.

가능한 범위에서:

- 상황
- 단계
- 당사자
- 핵심 문제
- 기본 문서
- 기본 금액
- 기본 일정
- 기본 목표
- 핵심 위험

을 파악한다.

사건이 단순하면 1차에서도 상당한 정보가 확보될 수 있다.

사건이 복잡하면 1차 질문이 더 많아질 수 있다.

### 2차

1차에서 만들어진 Profile을 출발점으로 하여 개인 사건을 더 깊게
재구성한다.

2차는 1차 질문을 다시 하는 단계가 아니다.

2차에서는 이미 확보된 정보를 전제로:

- 세부 사실
- 사건 경위
- 시간순서
- 당사자별 행동
- 계약/문서 조건
- 금액/지급
- 상대방 주장과 반응
- 사용자의 대응
- 손해/영향
- 증거
- 증거 간 관계
- 진술과 문서의 차이
- 핵심 쟁점
- 해결 목표

등 필요한 정보를 더 깊게 추적한다.

따라서 **2차가 1차보다 정보 밀도와 개인화 수준이 낮아지는 것은 실패**다.

## 51.7 2차 유료 가치 기준

유료 2차 검토는 단순히 질문을 몇 개 더 제공하는 상품이 아니다.

유료 검토를 선택한 고객에게는:

1. 이미 제공한 정보를 다시 묻지 않고
2. 이미 확보한 자료를 다시 요구하지 않으며
3. 새로운 사실을 단계적으로 확인하고
4. 답변 간 관계를 연결하고
5. 필요한 경우 증거를 추가로 요청하고
6. 모순 또는 불확실성을 구분하고
7. 사건의 경위를 구조화하고
8. 최종적으로 전문가 Handoff에 사용할 수 있는 수준까지
   Case Profile을 정교화한다.

이것이 유료 상세검토의 핵심 가치다.

## 51.8 Case Reconstruction Completeness

기존 Stop Condition을 단순한 결과 변화 여부만으로 해석하지 않는다.

최종 종료 기준은 **Case Reconstruction Completeness**이다.

다음의 중요한 항목이 현재 사건에서 필요한데 아직 비어 있다면
질문을 계속한다.

- 사건의 시작과 계기
- 주요 사건의 시간순서
- 관련 당사자
- 당사자별 역할과 행동
- 계약/문서와 핵심 조건
- 금액/재산/의무 관계
- 사용자의 주장
- 상대방/기관의 주장
- 실제 발생 사실
- 이미 취한 조치
- 상대방/기관의 반응
- 현재 상태
- 손해 또는 영향
- 관련 증거
- 증거의 출처와 의미
- 진술/문서/증거 간 불일치
- 핵심 쟁점
- 해결 목표
- 전문가가 사건을 시작하기 위해 반드시 알아야 할 추가 사실

단, 해당 항목이 현재 사건과 관계없는 경우에는 질문하지 않는다.

즉:

**필요한 정보가 남아 있으면 계속한다.**

**사건에 필요하지 않은 정보는 묻지 않는다.**

## 51.9 Stop Condition의 정확한 정의

다음은 Stop Condition이 아니다.

- 결과를 하나 만들 수 있다.
- CASE가 정해졌다.
- 위험도가 대략 계산되었다.
- 질문이 몇 개 진행되었다.
- 1차 결과와 비슷한 판단이 가능하다.
- 2차 질문이 충분히 길어 보인다.

진짜 Stop Condition은:

> 현재 Case Profile을 기준으로 해당 사건에서 전문가가 최초 설명을
> 다시 요구하지 않고 사건을 이해하고 다음 해결 단계로 들어갈 수 있을
> 정도로 중요한 사실이 확보되었으며, 남은 Unknown이 추가 질문을 통해
> 실질적으로 해결할 가치가 없는 상태.

이다.

## 51.10 질문의 Branch 원칙

질문은 미리 정해진 선형 목록이 아니라 사건의 답변에 따라 Branch된다.

예:

A 답변
→ 계약 조항 확인
→ 특정 조항 발견
→ 금액 확인
→ 지급일 확인
→ 상대방 행동 확인
→ 대응 여부 확인
→ 증거 확인

B 답변
→ 계약 취소 경위
→ 상대방 요구
→ 반환 약정
→ 반환 기한
→ 요청 기록
→ 상대방 반응
→ 증거 확인

동일한 CASE에서도 최초 입력과 앞선 답변에 따라 전혀 다른 질문 경로가
생길 수 있다.

## 51.11 질문과 선택지는 사건의 인과·관계 정보를 보존해야 한다

질문은 단순 분류값만 저장하는 방식으로 끝내지 않는다.

가능한 경우 다음 관계를 보존한다.

- Who did what
- To whom
- When
- Under what condition
- Based on which document
- For what amount
- What happened next
- How the other party responded
- What evidence supports the statement
- What remains uncertain

이 정보가 결과 및 Expert Handoff에서 사용될 수 있도록 Profile에 연결한다.

## 51.12 Evidence-First / Document-First 원칙

이미 확보된 문서나 자료가 특정 사실을 확인할 수 있다면
같은 사실을 불필요하게 질문하지 않는다.

문서에서 확인 가능한 사실:

Document / Evidence
→ Fact Extraction
→ Profile Update
→ Conflict Check
→ Next Missing Fact Question

으로 연결한다.

단, 문서가 제공되었다고 해서 문서가 의미하는 내용을 임의로 확정하지
않는다.

## 51.13 직접 입력은 질문 실패가 아니다

선택지에 정확히 맞지 않는 상황이 발생하는 것은 정상이다.

사용자의 직접 설명은:

Direct Input
→ Situation Extraction
→ Profile Update
→ Reclassification
→ 필요한 추가 질문

으로 처리한다.

직접 입력을 `other` 하나로 버리지 않는다.

## 51.14 질문과 결과의 연결

모든 질문은 다음 중 적어도 하나에 연결되어야 한다.

- Situation Profile
- Case / Resolution Path
- Risk
- Evidence Requirement
- Final Judgment
- Next Action
- Expert Handoff

질문에 답했는데 어느 곳에도 의미 있게 반영되지 않는다면
질문 또는 데이터 연결을 수정한다.

## 51.15 결과보다 Profile이 먼저다

VFBCAI는 결과를 만들기 위해 Profile을 단순화해서는 안 된다.

오히려:

Input
→ Profile
→ Questions
→ Evidence
→ Profile Refinement
→ Case Reconstruction
→ Result
→ Expert Handoff

의 순서를 유지한다.

**결과를 만들기 위해 질문을 줄이지 않는다.**

**질문이 충분히 진행된 결과가 자연스럽게 Result가 되어야 한다.**

## 51.16 Question Library는 지식 자산이다

Question Library에는 가능하면 다음 정보를 함께 관리한다.

- 질문
- 질문 목적
- 대상 Profile field
- 필요한 선행 사실
- 선택지
- 선택지의 실제 의미
- Branch 조건
- 필요한 Evidence
- 결과 연결
- Expert Handoff 연결
- 중복 방지 조건

따라서 질문 Library는 단순 UI 문구 모음이 아니라
VFBCAI의 전문 지식·판단 흐름을 축적하는 자산이다.

## 51.17 학습/축적 가능한 Case 자산

완료된 Case는 가능한 범위에서 다음 구조로 축적한다.

Initial Input
+ Answers
+ Direct Input
+ Evidence
+ Extracted Facts
+ Confirmed Facts
+ Claims
+ Inferences
+ Unknowns
+ Timeline
+ Parties
+ Key Issues
+ Resolution Path
+ Result
+ Expert Handoff

이 축적 데이터는 향후:

- 새로운 질문 설계
- 질문 Branch 개선
- 유사 사건 탐색
- 콘텐츠
- SEO / AEO / GEO / LLMO
- 전문가 업무 지원
- 서비스 품질 개선

등에 활용할 수 있는 구조적 자산이 된다.

단, 실제 저장/활용 범위는 개인정보·보안·법적 요건을 준수해야 한다.

## 51.18 Agent가 절대로 하지 말아야 할 해석

다음 해석은 금지한다.

> "ONE RESULT이므로 질문을 줄여야 한다."

> "UX가 간단해야 하므로 중요한 질문을 생략한다."

> "유료 단계라도 질문을 몇 개만 보여주고 결과로 넘어간다."

> "결과를 만들 수 있으므로 Profile이 충분하다."

> "질문이 많아 보이므로 임의로 질문을 제거한다."

> "2차 질문은 1차보다 짧아야 한다."

ONE RESULT는 **결과 화면의 개수**에 대한 원칙이지
**질문/프로파일링의 깊이를 줄이라는 원칙이 아니다.**

## 51.19 Agent의 구현 전 필수 검증

Architect는 구현 전에 반드시 확인한다.

1. 실제 전문가가 이 사건에서 무엇을 추적하는가?
2. 현재 Profile에 무엇이 이미 확보되어 있는가?
3. 무엇이 아직 중요한 Unknown인가?
4. 각 Unknown은 왜 중요한가?
5. 어떤 질문이 그것을 확인하는가?
6. 답변에 따라 어떤 Branch가 발생하는가?
7. 어떤 Evidence가 필요한가?
8. 이 질문이 이전 정보를 반복하지 않는가?
9. 이 질문이 Expert Handoff에 의미가 있는가?
10. 사건이 충분히 재구성되기 전에 Stop되지 않는가?

하나라도 답할 수 없으면 질문 설계를 확정하지 않는다.

## 51.20 Verifier의 필수 검증

Verifier는 단순히 "결과가 나왔다"를 PASS로 처리하지 않는다.

반드시 실제 브라우저에서:

- 단순 사건
- 중간 복잡도 사건
- 복잡한 사건
- 서로 다른 Branch
- 직접 입력
- Evidence 제공
- Evidence와 답변의 충돌 가능 상황

등을 검증하고, 사건 복잡도에 따라 질문 깊이가 자연스럽게 달라지는지
확인한다.

복잡한 사건에서 중요한 정보가 비어 있는데 질문이 조기 종료되면
FAIL이다.

단순한 사건에서 불필요한 질문을 계속하면 역시 FAIL이다.

즉 QA 기준은 **질문 수의 많고 적음이 아니라 사건 복원 품질**이다.

## 51.22 Master 확정 선언

이 문서부터 VFBCAI의 질문 개발은 다음 한 문장으로 판단한다.

> **VFBCAI는 질문을 줄이는 AI가 아니라, 사건을 추적하여 필요한 질문을
> 정확하게 선택하고, 증거와 사실을 연결하여 전문가가 바로 해결을
> 시작할 수 있는 수준까지 Case를 축적하는 AI다.**

복잡한 사건에는 복잡한 질문 흐름이 허용되고, 단순한 사건에는 단순한
질문 흐름이 허용된다.

질문의 수와 깊이는 사건이 결정한다.

이 원칙은 특정 서비스의 임시 규칙이 아니라
CHECK / VERIFY / REGISTER / PROTECT 전체에 적용되는
VFBCAI Universal Master 원칙이다.
