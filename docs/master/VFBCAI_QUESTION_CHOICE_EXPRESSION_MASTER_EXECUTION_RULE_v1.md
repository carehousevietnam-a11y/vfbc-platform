## 0. 최우선원칙

- 질문 개수는 고정하지 않는다. 1차 5개 / 2차 2개 같은 고정 공식은 사용하지 않는다.
- 필요한 사실이 남아 있으면 질문을 추가하고, 중요한 사실이 충분히 확보되면 종료한다.
- 1차는 Situation Skeleton을 만든다. 2차는 1차 답변을 전제로 개인화된 사실을 깊게 추적한다.
- 2차에서는 1차에서 이미 확인한 사실을 같은 의미로 다시 묻지 않는다.
- 질문은 실제 전문가가 사건을 재구성할 때 필요한 정보와 직접 연결되어야 한다.
- CASE_01~CASE_06 체계를 유지하며 CASE_07을 임의로 만들지 않는다.
- CHECK / VERIFY / REGISTER / PROTECT 구조, Master Funnel 구조, DB / API / CRM / Storage / RLS, Signup·기존 Result·확정 Business Logic, Phase1 / Phase2 역할 구분을 임의로 바꾸지 않는다.
- 질문 표현만 바꾸고 기존 answer key·Profile·분기의 **데이터 의미**가 달라지면 안 된다.

## 1. 질문은 조사·재구성 단위

각 질문은 최소 하나 이상의 Situation Profile, Case/Resolution Path, Risk, Evidence Requirement, Final Judgment, Next Action, Expert Handoff에 연결되어야 한다.

질문의 답변이 다음 질문이나 결과에 아무런 영향을 주지 않는다면 질문을 제거하거나 연결을 수정한다.

문서로 확인할 수 있는 사실은 질문으로 반복 수집하지 않고 Evidence → Fact Extraction → Profile Update → Conflict Check → Next Missing Fact의 순서로 처리한다.

Stop은 질문 수가 적어서가 아니라, 중요한 사실이 충분히 확보되어 전문가가 고객에게 처음부터 다시 묻지 않아도 사건을 이해할 수 있는 상태를 의미한다.

질문을 예쁘게 만드는 작업이 아니다. 각 질문은 반드시:

사용자 답변  
→ 실제 상황 의미  
→ Situation Profile  
→ 다음 조사 Branch  
→ 최종 판단  

으로 연결되어야 한다.

모든 질문은 다음 연결을 가져야 한다.

**질문 목적 → Profile field → Branch → Result/Judgment → Next Action**

결과와 연결되지 않는 질문은 구현·Brief에 포함하지 않는다.

### 1차 — Situation Skeleton

- 사건 유형/문서 성격
- 기관이 무엇을 요구하거나 문제로 보는지
- 사용자가 이해한 실제 상황
- 이미 한 대응
- 기한 및 현재 단계
- 확인하고 싶은 핵심 목표

### 2차 — Personalized Investigation

- 1차에서 남은 Unknown
- 실제 상황과 기관 설명의 차이
- 시간순서·구체적 사실
- 기관의 후속 반응
- 최초 제출/추가 제출 및 관계
- 금액·날짜·장소·행동 등 필요한 구체 사실
- 반복 요구·재보완·재출석 여부
- 증빙 및 현재 막힘
- 최종적으로 확인하고 싶은 목표

## 2. 표현은 사용자가 답할 수 있는 언어

현재 주요 사용자는 베트남어를 잘하지 못하는 외국인이다.

따라서 질문은 행정문서의 정확한 베트남어 문구를 읽었다고 가정하면 안 된다.

사용자는 다음 수준으로 답할 수 있어야 한다.

- 다른 사람에게 설명을 들었다.
- 번역을 받아 대략 이해했다.
- 교통국에서 무엇을 하라고 했다는 정도를 알고 있다.
- 문서의 정확한 표현은 모른다.

따라서 질문과 선택지는  
"문서에 정확히 무엇이라고 적혀 있었습니까?"  
보다  
"교통국에서 무엇이라고 설명받으셨나요?"  
같은 실제 기억 기반 표현을 우선한다.

사용자가 베트남어 행정문서를 직접 읽고 정확히 이해했다고 가정하지 않는다. '설명받은 내용', '번역받은 내용', '대략 이해한 내용'으로도 답할 수 있어야 한다.

다음과 같은 상황에서도 답할 수 있어야 한다.

- 다른 사람이 설명해 줌
- 통역/번역을 통해 들음
- 기관 직원에게 구두로 설명받음
- 문서를 가지고 있지만 내용을 잘 모름
- 문서의 일부만 이해함

따라서 질문에서  
"문서에 정확히 무엇이라고 적혀 있습니까?"  
같은 방식으로 답변을 강제하지 않는다.

필요한 경우:

"교통국에서 어떻게 설명받으셨나요?"  
"무엇을 하라고 들으셨나요?"  
"설명받은 내용과 실제 상황을 비교하면 어떤가요?"  

처럼 사용자의 기억/이해 수준에서 답할 수 있도록 한다.

'모르겠습니다'를 기계적인 공통 선택지로 반복하지 않는다. 무엇을 이해하지 못했는지 맥락으로 표현한다.

기계적인:

- 모르겠습니다
- 기타
- 잘 모르겠습니다

를 사용하지 않는다.

외국인 사용자가 실제로 겪는 상황으로 표현한다.

예:

- 왜 돈을 내야 하는지 설명받지 못했거나 정확히 이해하지 못했습니다.
- 무엇을 문제로 보는지 설명받지 못했거나 정확히 이해하지 못했습니다.
- 무엇을 해야 하는지 설명받지 못했거나 정확히 이해하지 못했습니다.

단, 이미 적절한 표현이 있으면 불필요하게 바꾸지 않는다.

Direct Input 선택지는 반드시 아래 문구를 그대로 유지한다.

**위에 내용이 없거나 설명이 필요합니다 → 직접 입력**

문구를 변경하거나 뒤에 설명을 추가하지 않는다.

Direct Input은 `other` 대체용이 아니다. 반드시:

Direct Input  
→ Note 저장  
→ Profile 반영  
→ 다음 질문/Branch  
→ 필요 시 CASE 재분류  
→ Result 영향  

의 실제 데이터 흐름을 유지한다.

## 3. 선택지는 상황압축데이터

선택지는 단순 UI 옵션이 아니다.

선택지는 반드시 서로 다른 실제 상황을 의미해야 한다.

각 선택지는 가능한 경우:

Answer  
→ Profile 값  
→ Fact Type  
→ 다음 질문  
→ Skip  
→ 추가 추적  
→ 결과 판단  

중 하나 이상의 실제 로직을 발생시켜야 한다.

모든 선택지가 동일한 다음 질문으로 연결된다면  
그 선택지는 상황추적 관점에서 충분히 설계되지 않은 것이다.

따라서 개발자는 질문을 추가하기 전에  
기존 선택지가 실제 branching에 사용되고 있는지를 먼저 확인한다.

한 질문의 선택지는 서로 다른 실제 상황을 의미해야 한다.

선택지끼리 의미가 겹치면 안 된다.

추상어(예: 서류 관련, 문제가 있음, 기타)를 기본 선택지로 사용하지 않는다.

외국인이 베트남어 문서를 직접 읽지 못해도 자신이 들은 설명을 기준으로 선택할 수 있어야 한다.

'모름'이 필요한 경우 무엇을 몰랐는지를 상황에 맞게 표현한다.

선택지는 질문마다 최대 4~5개의 실제 상황으로 구성하고 여기서 선택지를 종료한다.

4~5개의 대표 상황으로 선택지를 종료한다. 그 이후에 또 다른 일반 선택지를 추가하지 않는다.

마지막 선택은 항상 **위에 내용이 없거나 설명이 필요합니다 → 직접 입력**으로 통일한다.

Direct Input은 저장·Profile 반영·재분류·추가질문의 실제 데이터 경로여야 한다.

선택지는 **짧게** 만드는 것이 목표가 아니다 — **서로 다른 실제 상황**을 의미해야 한다.

각 선택지는 가능한 경우: Profile 값 · Fact Type · **다음 질문 / Skip / 추가 추적 / 결과 판단** 중 하나 이상 발생.

**모든 선택지가 동일 후속 질문** → 상황추적 관점 **미설계** — 구현 전 기존 branching 사용 여부 **먼저 확인**.

맞지 않으면 **직접 설명 입력** → Profile 보존 (numbered option 아님).
