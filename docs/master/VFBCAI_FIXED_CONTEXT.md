# VFBCAI 고정 컨텍스트 — 확정 사항 (해석·재설계·재제안 금지)
■ 0. 이 문서의 사용 규칙 (모든 AI 도구 공통: ChatGPT / Claude / Cursor)
- 이 문서의 내용은 모두 이미 결정·LOCK된 사항이다. 다시 묻거나, 대안을 제안하거나, "더 나은 구조"를 제시하지 않는다.
- 요청 범위 밖의 화면·구조·흐름·DB·UI를 언급하거나 수정하지 않는다.
- 이 문서와 충돌하는 판단이 필요하면 임의로 결정하지 않는다. "충돌 항목: ○○"으로 표시하고 멈춘다.
- 이 문서를 수정할 수 있는 사람은 대표(Ace)뿐이다.
■ 1. 프로젝트 개요
- VFBCAI(베트남 외국인 비즈니스 검증·등록 AI 센터), vfbcai.com
- 대상: 베트남에서 법률·행정 절차를 처리해야 하는 외국인(주로 한국인). 베트남어를 몰라도 이해할 수 있어야 한다.
- 4개 축: CHECK(자격/비용/서류/절차 확인) / VERIFY(계약·부동산·세무·사기 검토) / REGISTER(인허가 등록대행) / PROTECT(만료일·서류 사후관리)
- 기술: Next.js / TypeScript / Supabase / OpenAI / Vercel
■ 2. 역할 분담 (고정)
- 대표(Ace): 기획·승인·최종 결정
- Claude: 분석, 검토(브라우저 점검 포함), Cursor 지시서 작성, Cursor 결과 검토
- Cursor: 구현, 자체 QA, DB/Storage 읽기 검증, git commit
- ChatGPT: 콘텐츠 원문 작성 + MASTER 기준 점검 + 범위 통제. 배치당 1회만 관여.
- ChatGPT는 코드·구현 방식·화면 설계를 지시하지 않는다.
■ 3. 확정·LOCK 사항 (수정 금지)
- 행정문서(Admin) VERIFY = MASTER. 질문/선택지/표현, 1차·2차 업로드, 1차 결과, 회원가입 모두 완료·동결.
- Admin MASTER는 읽기 전용 기준이며 import만 한다. 예외는 대표가 승인한 서비스 중립 슬롯(예: 2차 서류 이동 규칙의 서비스 중립화)뿐이다. 그 외에는 수정·재작업을 금지한다. 새 중립 슬롯이 필요하면 대표 승인을 먼저 받는다.
- 고객 퍼널(확정):
  Situation Profile(내부 추적용, 고객에게 비노출)
  → 적응형 MASTER 질문(Stop Condition 충족 시 종료)
  → 회원가입 1회(결과 직전)
  → 결과
  → 무료: 1차 결과 → 마이페이지("전문가 진행하기" 버튼)
  → 유료: 2차 개인화 질문 + 상세 자료 업로드 → "종합 결과 보기" → 마이페이지(간단 결과 + "AI 리포트 보기" + "전문가 진행하기")
- "전문가 진행하기"는 결제 화면으로 바로 보내지 않는다. 전문가 페이지에서 2차 질문·서류 제출만 활성화되고, 유료 기능은 결제 후 열린다(결제는 별도 미션).
- 선택지 밀도: 질문당 4~5개 + 직접입력. 단순 Yes/No 금지. 실제 상황을 구분하는 선택지로 만든다.
- 결과 구성 방향: 공통 40% / 개인화 60%
- V1 범위: 통제 가능한 적응형 시스템(검증된 질문 라이브러리 + 명확한 분기 규칙 + Stop Condition). AI 완전 자동 분류는 V2.
- 일반적인 케이스는 퍼널이 끝까지 처리하고, 특수·복잡 케이스는 "전문가 진행"으로 보낸다.
■ 4. 빌드 원칙 (Clean Build)
- 엔진 1개(Admin MASTER) + 서비스별 Content Pack을 새로 작성한다.
- 기존 서비스 코드·구 엔진·번역표·옛 페이지·폐기된 초안은 절대 가져오지 않는다.
- "내용만 다르다"의 의미: 프레임워크(프로파일링, 질문·선택지·표현 밀도 규칙, 흐름)는 그대로 쓰되, 각 서비스의 문맥과 문장은 해당 도메인에 맞게 새로 쓴다. 행정문서 문장에서 단어만 바꾸는 방식은 금지한다.
- 같은 값 = 같은 의미/라벨: 선택 → 저장 → 요약 → 재방문 → 결과 → 마이페이지 전 구간에서 일치해야 한다.
- UI·편집·정렬은 Admin MASTER와 처음부터 동일하게 한다.
- 지정된 서비스 화면 외에는 수정하지 않는다(확정된 마이페이지 등 포함).
- 레거시 코드는 새 서비스가 LOCK된 뒤 일괄 삭제한다.
- 빌드 중 발생한 문제는 크기와 관계없이 lessons ledger에 누적하고, 다음 구현에 반영한다.
- 서비스 브랜치는 main에서 새로 딴다. 다른 서비스 브랜치에 문서·코드를 섞지 않는다.
■ 5. 진행 규칙 (Cursor 작업 공통)
- 커밋·푸시·병합은 대표 승인 후에만 한다. 지시서에 승인 범위가 적혀 있으면 그 범위까지만 한다.
- 커밋할 파일은 경로를 지정해 스테이징한다(git add . / -A / commit -a 금지).
- 작업 중단 조건은 "추적 중인 파일의 수정"이다. untracked 파일만 있으면 건드리지 않고 진행한다.
- 테스트 신청 데이터는 삭제하지 않는다.
- 실제 DB/Storage 값을 읽어 확인하지 못한 항목은 PASS로 쓰지 않는다. "NOT VERIFIED"로 분리 표기한다.
- 보고는 요약표 + 이상 항목만 쓴다.
- handoff 파일(NEXT/REPORT)은 저장소의 기존 handoff 규칙에 따라 매 작업마다 갱신한다.
■ 6. 현재 진행 상태 (2026-10-08 기준)
- 행정문서(Admin): 완료·LOCK
- 부동산 VERIFY: Clean Build 마감 QA 통과, 푸시 완료(main 병합 전)
- 다음: 사기 → 세금 → 기타/불명확
  (10/7 결정: 부동산 이후 나머지 VERIFY 서비스는 Cursor 별도 창에서 병렬 빌드하고, 대표가 일괄 검토한다)
■ 7. 사기(Fraud) VERIFY 콘텐츠 필수 요구사항
① 첫 분기: "피해 전 검증"(송금·계약 전에 상대를 확인) vs "피해 후 대응"(이미 송금·손해 발생). 두 경로는 질문 흐름을 분리한다.
② 긴급 Stop Condition: "지금 송금 요청을 받는 중" 또는 "송금 후 72시간 이내"이면 추가 질문 없이 즉시 행동 안내(은행 지급정지 요청, 공안 신고)를 제시하고 전문가 진행으로 연결한다.
③ Situation Profile 필드 후보: 사기 유형(투자·동업 / 취업·비자 대행 / 임대 보증금 / 온라인·메신저 / 공공기관 사칭) · 진행 단계 · 금액대 · 지급 수단(베트남 계좌 이체·현금·코인 등) · 보유 증거(계약서·채팅·영수증 등) · 상대 신원 확인 수준(개인/법인, 사업자번호 유무) · 신고 여부 · 고객 목표(송금 차단·회수·신고·상대 검증)
④ 타 서비스 경계 라우팅: 임대 보증금 사기 ↔ 부동산, 공안·세무서 사칭 ↔ 행정문서. 어느 쪽으로 보낼지 규칙으로 명시한다.
⑤ 결과 문장은 "사기입니다"처럼 단정하지 않는다. "위험 신호 N개 확인" 같은 신호 기반 표현을 쓴다.
⑥ 전문가가 실제로 판단할 수 있는 핵심 정보가 프로파일에 남아야 한다.
■ 8. 금지 사항
- LOCK된 Admin/부동산 구조·문구 수정 금지(승인된 중립 슬롯 제외)
- 요청 없는 새 화면, 새 퍼널 단계, 새 결제 흐름 추가 금지
- 레거시 서비스 페이지 내용 참고·인용 금지
- 범위를 넓혀야 할 때는 대표에게 먼저 묻는다
■ 9. 질문·선택지 설계 표준 (모든 서비스 공통, 대표 확정)
9-1. 플랫폼 목적
- VFBCAI의 목적은 베트남어를 전혀 모르는 외국인이 각 항목을 처리할 때 가장 많이 겪는 문제를, 아주 디테일하고 정확하게 최대한 많이 정보로 축적하는 것이다. 이 축적이 독보적인 플랫폼의 근거다.
- 마지막 리포트는 이 정보를 최대한 많이, 디테일하고 정확하게 뽑아 제공한다. 그것이 고객 신뢰의 근거다.
- 질문이나 선택지의 개수를 늘리는 것이 목표가 아니다. 질문 하나, 선택지 하나에서 얻는 정보의 정밀도와 깊이(정보 밀도)를 높이는 것이 목표다. 개수는 4~5개 + 직접입력(3절)을 유지한다.
9-2. 대상 고객 기준
- 고객은 베트남어를 전혀 모르고 베트남 행정·세무·법률 체계에 익숙하지 않은 외국인이다.
- 전문가 수준의 프로파일링을 유지하되, 베트남어를 모르는 외국인이 자신의 실제 경험만으로 이해하고 선택할 수 있는 자연스러운 생활 언어로 표현한다.
- 쉽게 쓰는 것과 정보를 적게 얻는 것은 다르다. 쉬운 표현이어도 얻는 정보는 줄이지 않는다.
- 전문 용어는 없애지 않는다. 용어와 실제 상황을 함께 적는다. 예: "VAT — 회사에서 물건·서비스를 사고팔며 생기는 세금과 신고 내용을 확인하고 싶습니다."
- 선택지는 고객이 자기 경험을 읽고 자기 상황을 찾는 문장이어야 한다. 저장값(필드 값)은 영문 코드로 분리한다.
9-3. 질문 2단 정보 구조 (최소 기준)
- 모든 핵심 질문은 최소 2단 정보 구조로 설계한다.
  ① 상황을 구분하는 정보(대상·종류·단계)
  ② 그 상황을 구체화하는 정보(원인·상태·기한·기관·증거·대응 이력 등)
- 하나의 질문에서 이 두 정보 층을 자연스럽게 함께 수집한다. 그리고 다음 질문은 앞서 확보한 정보에 따라 더 정밀하게 분기한다.
- 2단 구조는 질문 수를 늘리라는 뜻이 아니다. 질문 한 개당 정보 밀도를 높이라는 뜻이다. "질문을 두 개 만든다"로 해석하지 않는다.
9-4. 선택지 2단 정보 구조 (최소 기준)
- 선택지 한 문장은 최소 2가지 이상의 정보 층위를 함께 담는다. 예: 대상 + 상황, 사건 + 상태, 상황 + 고객 목적, 상태 + 증거.
- 고객이 하나를 선택하면 내부에서 2개 이상의 필드로 분해해 저장한다. 선택 자체가 데이터가 되어야 한다. 선택지마다 "분해 규칙(어느 필드에 어느 값으로 저장하는지)"을 Content Pack에 명시한다.
- 예: "회사에서 매출이나 매입 거래를 했고, VAT 신고 내용이 실제 거래와 맞는지 확인하고 싶습니다." → 법인 / VAT / 매출·매입 거래 / 신고내용 확인 / 실제 거래 대조 필요, 로 분해 저장.
- 같은 정보를 담은 선택지를 중복하지 않는다. 서로 다른 실제 상황을 구분한다. Yes/No 금지.
- 한 선택지에 서로 다른 값이 섞여 저장되지 않게, 분해 규칙은 값 1:1로 정의한다(같은 값 = 같은 의미/라벨).
9-5. 외국인이 가장 많이 겪는 문제 반영
- 각 서비스의 질문·선택지는 해당 서비스에서 외국인이 처리 중 실제로 자주 막히는 지점(서류 이해 불가, 기한 모름, 기관 요구 사항 불명확, 비용·절차 불확실, 사기·분쟁 위험 등)을 구분하도록 설계한다.
- 각 선택지는 "전문가가 이 정보로 실제 판단을 할 수 있는가"를 통과해야 한다(전문가 판단용 정보가 프로파일에 남는다).
9-6. 리포트 연결
- 모든 저장 필드는 리포트에서 다시 쓰인다. 리포트에 쓰이지 않는 필드는 만들지 않는다.
- 리포트(유료)는 1차 + 2차에서 축적한 정보를 최대한 활용해 디테일하고 정확하게 작성한다. 단정 표현은 피하고 확인된 사실 중심으로 쓴다.
- 결과 문장의 변수 자리에는 저장값이 아니라 고객용 라벨을 넣는다.
9-7. 서비스별 Content Pack 작성 시 필수 체크(원문 제출 전 자체 점검)
- [ ] 외국인이 베트남어를 몰라도 이해할 수 있는가
- [ ] 질문 하나가 2단 정보를 담고 다음 질문이 그에 따라 분기하는가
- [ ] 각 선택지가 2가지 이상 정보를 담고 분해 규칙이 명시되었는가
- [ ] 전문가가 판단할 수 있는 정보가 프로파일에 남는가
- [ ] 저장 필드가 모두 리포트에 쓰이는가
- [ ] 고정 문서 3·4절과 충돌하지 않는가
9-8. 적용 범위
- 신규 서비스(세금, 기타/불명확)는 처음부터 이 표준을 적용한다.
- 이미 구현된 서비스(Admin, 부동산, 사기)에 소급 적용할지는 대표가 따로 지시할 때만 한다. 지시가 없으면 수정하지 않는다.
